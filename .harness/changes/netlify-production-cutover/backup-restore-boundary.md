# 源备份与目标恢复的操作边界

2026-09-06。状态：操作设计，未取得真实备份、未恢复或迁移生产数据。

## 已核实平台事实

- Zeabur 在线 PostgreSQL 备份为 pg_dumpall 的 SQL，覆盖服务中所有数据库；平台只限时保留。
  因而需要下载独立副本，不能把某次源代码发布或备份任务已启动当作完整备份。
  [Zeabur 官方备份说明](https://zeabur.com/docs/zh-CN/operations/data/backup-restore)
- pg_dump 客户端不能导出比自己主版本更新的服务器；导出内容导入更旧主版本也不保证兼容。
  已看到源镜像 postgres:18，不等于查询确认了服务端版本；本地合成PG17更不代表目标生产版本。
  [PostgreSQL 官方 pg_dump 说明](https://www.postgresql.org/docs/current/app-pgdump.html)
- Netlify 的应用发布回滚不会自动回滚数据库；数据库备份恢复替换生产分支内容，备份后写入可能丢失。
  不能以应用回滚成功代替数据回滚验证。
  [Netlify 官方备份与恢复说明](https://docs.netlify.com/build/data-and-storage/netlify-database/backup-and-recovery/)

## 具体执行顺序（先决信息待取得）

1. 稳定访问源端后核对服务ID、连接到的数据库/schema、服务端版本、扩展和基线表。
   记录只读盘点输出；43张表只是白名单，不代替额外表/文件对象清单。
2. 备份完成后将原始文件保存到受限、Git忽略且不公开的明确目录。记录时间、大小、SHA-256、
   来源服务、状态；不将内容、下载授权URL、数据库角色信息或凭证写进日志/报告/Git。
3. 先在同主版本、无生产连接/外网/持久业务挂载的独立恢复环境验证全份备份。
   必须确认归属/范围再运行还原，不能把集群级SQL直接送入现有Netlify生产库。
   逐项记录还原错误，不能忽略非零退出后继续宣称恢复成功。
4. 在恢复副本中选定ARC库，核对业务表、扩展、逻辑引用与任务状态。若包含其他数据库或全局对象，
   不将其擅自并入ARC目标。明确目标版本和托管权限后再确定选定库导出及owner/ACL映射方案。
5. 在隔离目标环境执行拟定导入，校验表/主键集合、内容摘要、引用、序列及业务汇总；
   模型或通知凭证只通过已有授权绑定处理，不随SQL导入后自动启用外发。
6. 导入成功仍不代表旧任务可续跑：queued/running/waiting-review/uncertain需按旧账本与原生
   checkpoint转换验证。无状态转换证据就继续保留旧平台主写。
7. 真正切流前冻结源端新提交/调度/领取，处理在途已知与未知结果，取得最终一致备份/增量及对账。
   产生目标新写入后的回滚必须单独冻结、回迁并对账，不能只改前端代理。
