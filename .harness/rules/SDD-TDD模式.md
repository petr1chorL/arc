# ARC.ONE SDD-TDD 模式

## 规格真相

SDD 的规格入口保持为 `.scratch/<feature>/PRD.md`、具体 Issue 和已确认的
`docs/superpowers/specs/` 设计。`.harness/changes/` 只保存执行回执，不复制规格真相。

发生冲突时遵循 `.harness/README.md` 的优先级。

## TDD 规则

行为变化默认执行：

1. 从 Issue 验收标准、边界和失败路径选一个可观察行为。
2. 编写聚焦测试并确认它因目标行为缺失而失败。
3. 写使该测试通过的最小实现。
4. 运行相邻回归；必要时在测试保护下重构。
5. 在 Issue 处理记录中保存 RED、GREEN 和最终验证命令。

缺陷先建立稳定复现和根因证据，再进入 RED。

## 适用边界

- 业务规则、权限、Workspace 隔离、状态机、契约、失败关闭和恢复路径必须测试先行。
- 纯文档、注释和不改变行为的机械调整不要求虚构失败测试，但要执行针对性的静态完整性检查。
- 覆盖率是风险信号，不替代 TDD；仓库未配置统一覆盖率门禁时，不得伪造“≥80% 已通过”。

## 完成证据

测试只能证明其覆盖的行为。FakeGateway、Mock、演示数据和本地自动验收不能替代真实业务或生产签收。
