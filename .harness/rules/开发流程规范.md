# ARC.ONE Harness 开发流程

## 定位

Harness 作为执行层嵌入现有流程，不替换 Matt Pocock 项目管理链或 Superpowers 开发纪律。

```text
CONTEXT / PRD / Issue / Triage
→ 第一性原理核查
→ Brainstorming / Design
→ Writing Plan
→ TDD 实现
→ Spec + Standards Review
→ Verification
→ Handoff / 人工签收
```

详细要求以 `docs/PROJECT_WORKFLOW.md` 和 `AGENTS.md` 为准。

## 变更回执

从 `.harness/changes/_TEMPLATE/` 创建回执时必须填写：

- `.scratch/<feature>/PRD.md` 路径。
- 一个具体 Issue 路径。
- 已确认设计和计划路径（适用时）。
- 当前阶段、影响面、验证证据与遗留人工动作。

回执不得新增独立需求、改变 Issue 状态或成为新的 Acceptance 事实入口。Issue 的 AC、状态和处理记录
仍只在 `.scratch/<feature>/issues/` 维护；长期事实仍写入 `docs/`、源码或测试。

## 阶段门禁

| 阶段 | 入口 | 出口 |
|---|---|---|
| 澄清 | 用户意图与当前事实 | 范围、非目标、标准术语明确 |
| 规格 | PRD / Issue | AC 可观察、失败路径可测试、依赖明确 |
| 设计 | 已 Triage 的 Issue | 用户确认的方案和准确文件计划 |
| 实现 | 已确认设计/计划 | RED → GREEN，小而可审查的改动 |
| 审查 | 代码、测试、文档 | 0 个阻断问题；无范围漂移和能力夸大 |
| 验证 | 审查通过的变更 | 新的聚焦、回归、lint/build 和必要的浏览器/部署证据 |
| 收口 | 验证证据 | Issue、长期文档和回执同步 |

## 特殊场景

- Hotfix：可缩短设计文档，但不得省略复现、TDD、审查、安全边界和验证。
- 纯文档：不执行无意义的代码测试；必须检查链接、事实优先级、命令、占位符和 diff。
- 探索：不得把 Spike 或 PoC 描述成已交付能力。
- 棕地重构：不以模板风格为理由迁移目录；先证明具体摩擦和收益。

## 禁止事项

- 不读取或输出 `.env`、Key、Token 或私钥。
- 不为通过模板检查而引入仓库未采用的工具或目录。
- 不把 `.harness/wiki`、`changes` 或 `CONTEXT.md` 变成第二事实入口。
- 不把计划、Mock、自动技术验收或页面占位误报为生产能力。
