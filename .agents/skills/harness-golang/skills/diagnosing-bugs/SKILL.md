# Bug 诊断技能（Diagnosing Bugs）— Go 版

> 核心原则：**在建立稳定复现的反馈循环之前，禁止跳到"猜原因"阶段。**

## Phase 1 — 建立反馈循环

**这是整个技能的核心。** 如果你有一个能稳定复现 Bug 的**红/绿信号**，你已经完成了 90% 的工作。

### 构建反馈循环的方式（按优先级排列）

1. **失败测试** — 在能触达 Bug 的接缝处写 `go test` 单元/集成测试
2. **Curl / HTTP 脚本** — 针对运行中的 `go run .` 或编译后的二进制
3. **CLI 调用** — 带 fixture 输入，比对 stdout 与已知正确快照
4. **Playwright 无头浏览器脚本** — 驱动 UI，断言 DOM/console/network
5. **重放录制的 trace** — 保存真实请求/事件日志到磁盘，隔离重放
6. **临时测试桩** — 启动最小 `{{HTTP_MOCK_UTIL}}` + Mock 依赖
7. **二分法测试桩** — 如果 Bug 在两个已知状态之间出现，自动化"启动状态 X → 检查 → 重复"以便 `git bisect run`
8. **对比测试** — 同一输入跑旧版 vs 新版，对比输出

### 核心原则
- **要有侵略性，要有创造力，拒绝放弃。** 花不成比例的时间在这里。
- **收紧循环**：让它更快（缓存 setup，跳过无关初始化）、信号更清晰（断言具体症状）、更确定（固定时间，随机种子）
- **非确定性 Bug**：目标不是干净的复现，而是**更高的复现率**。循环跑 100 次，并行化，加压力。

### 如果实在无法建立反馈循环
停下来，明确说出你尝试了什么。向用户请求访问权限或 artifact。

**禁止在没有反馈循环的情况下进入 Phase 2。**

## Phase 2 — 复现 + 最小化

运行反馈循环，确认 Bug 出现。然后将复现条件缩小到**最小场景**。

## Phase 3 — 假设

生成 **3-5 个排序的假设**。每个假设必须是**可证伪的**："如果 <X> 是原因，那么 <改变 Y> 将让 Bug 消失。"

**向用户展示排序列表，再开始测试。**

## Phase 4 — 探测

每个探测对应 Phase 3 的特定预测。**一次只改一个变量。** 用 `{{DEBUG_TOOL}}` 调试器或 `{{DEBUG_TOOL}}` 检查状态。

## Phase 5 — 修复 + 回归测试

**先写回归测试，再修复。** 用 `go test` 写失败测试 → 看它失败 → 应用修复 → 看它通过 → 用原始场景重新运行 Phase 1 循环。

## Phase 6 — 清理 + 事后分析

- [ ] 原始场景不再复现
- [ ] 回归测试通过（`{{TEST_CMD}} {{RACE_DETECT_ARG}}`）
- [ ] 所有调试探针已移除
- [ ] 正确的假设写入 commit message

**然后问：什么能阻止这个 Bug？** 如果答案是架构变更，交给 `/arch-review-golang` 技能处理。
