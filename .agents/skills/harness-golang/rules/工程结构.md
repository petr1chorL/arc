## 2. 模块职责与依赖方向

| 模块 | 职责 | 允许依赖 |
|------|------|---------|
| `common/` | 公共库（错误码、JWT、工具） | 无（仅标准库 + 基础第三方库） |
| `<service>/api/` | HTTP API 入口 | common, 本 service rpc client |
| `<service>/rpc/` | 内部 RPC 服务 | common, models |
| `<service>/models/` | 数据模型 | common, 数据库驱动 |
| `tests/` | 测试 | 全部（仅测试作用域） |

**依赖方向（单向，不可逆）**:

```
common  ←  models  ←  rpc  ←  api  ←  tests
   ↑_________↑_________↑______↑
      （上游永不依赖下游）
```

---

## 3. 架构铁律

| 规则 | 描述 |
|------|------|
| R1 | **Service 之间禁止直接依赖内部实现** —— 只能通过 RPC 通信 |
| R2 | **common 禁止依赖任何业务模块** —— 它是最底层基座 |
| R3 | **API Handler 禁止直接调用业务逻辑** —— 必须经 Logic 层 |
| R4 | **API 禁止复制 RPC 业务规则** —— 仅做 HTTP 路由和参数校验 |

## 6. 新增模块/feature 的目录约定

- 新服务 → 新建 `<service>/` 目录，在 go.mod 中维护
- 新 API 端点 → 在 `<service>.api` 中定义，goctl 生成
- 新 RPC 方法 → 在 `<service>.proto` 中定义，goctl 生成
- 新需求 → 在 `.harness/changes/<id>/` 建档
