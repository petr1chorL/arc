# 原生执行控制旧接口的安全兼容设计

本切片继承生产迁移设计，只处理旧手动领取与 Run 删除两个已记录的契约缺口，不改生产配置。

## 底层目标

旧客户端得到可解释的迁移响应，而不是路径失踪；任何响应都不能使用户误以为运行已被取消、
外部动作被撤回或历史记录已删除。所有分支先经过 Session、CSRF、Workspace 和 run.execute。

## 手动领取

`POST /execution-jobs/next` 经授权后返回 410，说明已由原生异步执行器接管、不提供同步领取。
记录 `execution_job.process_next` denied 审计并提交该事实，不调用旧 Worker、外部 Gateway 或领取任务。
缺失身份 401，缺 CSRF/权限 403，跨 Workspace 404；保持已有共享 HTTP Origin 校验。

## 删除评估与范围边界

旧 Python delete_run_records 删除人审、产出物、黄金样本等关联对象；新增原生 Operation、effect、
checkpoint、整改、回归和调度记录必须保留证据。原表多数关联为逻辑引用而非 FK，仅查引用数为零
再 DELETE 无法排除已读取 Run 的并发写入；单独锁 Run 也不能阻断不遵守相同锁规约的引用创建。
不能为给出 204 而顺手增加软删除字段、修改所有查询语义或静默级联销毁原生账本。

已向主线程回报选择：当前最小契约为已存在 Run 返回明确 409 并保留记录；缺失/跨 Workspace 404。
若要求可见的删除成功 204，需单独明确软删除/归档契约或全引用写入锁规约后再实现，不能假装已兼容。
主线程已确认采用该过渡拒绝契约：所有既存 Run 都返回明确 409，注明“运行删除能力尚未迁移”，
不判断其为可删、已取消或已完成；查询只确认当前 Workspace 的 Run 存在并记录其原状态。
保留所有终态、未终态、needs_reconciliation、effect、Operation、checkpoint 与关联业务数据。
此端点存在性改善不计作功能等价补齐，删除成功能力仍是迁移缺口。

## 对抗式验收

- 410/409 不是成功领取、取消或删除。
- 拒绝审计持久化，但未修改 Run、Operation、effect、checkpoint 或业务引用。
- 无认证和无权限调用不绕过共享校验直接返回内部迁移说明。
- 当前不承诺旧 DELETE 的成功分支已完成，也不解除生产迁移阻断。
