# Workflow 云端门禁请求生命周期修复

范围来源：用户授权评估并完成迁移；本切片只修复已复现的本地/CI 门禁问题，不改变生产配置。

## 第一性原理与证据

版本治理需证明持久化的两个不可变版本，不能将错误 JSON 当成数组。9 项浏览器门禁重放在
最后版本读取复现 HTTP 429，正文为“请求过于频繁，请稍后再试”。既有 120 次/分钟客户端
限流保留。Workflow 量规目录的 effect 已清理后仍继续请求每个量规版本；StrictMode 与刷新
使无效请求消耗真实配额。Agent 目录已有对应的 active guard，量规目录缺失。

另一个独立确定失败是 E2E 将 Vite `/src/api/notifications.ts` 静态模块识别为通知执行。

## 最小设计

- 在量规目录初始请求结束后、启动版本子查询之前检查 effect 是否仍有效。
- 用延迟目录响应 + 页面卸载测试先证明旧实现仍发子查询；不通过加限额、重试或吞错来过门禁。
- 浏览器监视器区分同源静态资源与 `/api/` 业务执行路径，继续禁止外域及运行/通知 API。
- 版本读取先断言 HTTP 200，再核对响应与不可变快照。

## 对抗式边界

此修复只阻止失效 effect 扩大请求；不是所有 N+1 的批量化，也不声称生产无限规模目录不受限流。
没有放宽 Origin、CSRF、权限或全局限流。若仍有 429，应继续处理已证实的请求浪费，不隐藏错误。
