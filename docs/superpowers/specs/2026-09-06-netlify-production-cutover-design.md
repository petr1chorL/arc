# Netlify 生产切流与 Zeabur 退役设计

授权来源：用户于 2026-09-06 要求“做完 5、6”；继承已确认的原生迁移 PRD、
单主写入、备份对账和稳定观察后退役约束。不是对任意删除、未知费用或丢弃任务的授权。

## 底层目标与阶段

目标是完整业务和数据迁入 Netlify，并可证明恢复能力；不是仅将前端指向新 API。
阶段：compatibility（Zeabur 主写）→ isolated-preview → frozen → native-primary → observed → retired。
不能越过备份、非终态清点或对账阶段；每阶段记录精确 SHA、部署 ID 和检查结果。

## 先决装配

- 全域纯 router 组合已验证身份/资产/Workflow/运行模块，不携带本地测试服务器的合成身份或控制端点。
- Runtime 依赖从显式非密钥配置读取 Workspace/host/SecretRef 精确绑定；仅执行时由平台读取引用。
  没有正确绑定时禁止外部调用，不以全局 Key 隐式替代。
- 生产 API、AWL consumer、Scheduled tick 使用同一模式门禁；初始关闭且保持现有代理。
- 五条旧路由差异逐项收口：Provider 草稿迁移、Provider 配置检查、HTTP Tool 测试、Run 删除、
  旧 Worker 手动领取。最后一项以明确退役响应代替任意用户触发同步 Worker。
- Preview 与生产的数据、任务事件和配置边界必须实际验证，不能直接把合成 seed 发布到生产。

## 数据迁移与单主约束

1. 在原平台只读盘点数据库、挂载、业务表/列、逻辑引用、模型/通知配置名及非终态数量，不输出明文 Secret。
2. 生成源备份并记录大小/校验值，独立环境恢复后逐表核对，备份不进入 Git 或公开 artifact。
3. 停止新运行/新调度提交和新 Worker 领取；在途外部调用须落入已知结果。
   不得擅自取消真实人工任务、将未知结果伪造为成功或用空库替代原数据。
4. 若仍有跨平台续跑需求，必须额外验证旧 NodeRun/Artifact/HumanTask 到原生检查点的显式转换；
   未确定前保持原平台主写。旧 execution_jobs 不能通过复制表自动变成原生 Operation。
5. 冻结后完成最终备份/增量导入；校验所有表行数、主键/内容摘要、逻辑引用、状态及业务数值汇总。
6. 同一版本切换前端能力和 API；真实登录、运行、审核、评分、通知及审计闭环全部通过。

## 回滚和观察

新平台尚无新业务写入时，可恢复旧入口；产生新写入后必须先冻结并回迁/对账新增数据，
不能只改代理。Netlify 发布回滚不会自动恢复数据库快照，应用和数据库恢复必须分别确认。
稳定观察时长和可接受错误/未结算任务以实际负载与回滚窗口记录，不虚构已经观察。
满足后优先暂停旧资源并保留可恢复备份；永久删除数据库等不可逆动作必须在精确目标处确认。

## 验收

- 精确 SHA 的 GitHub CI、Netlify 构建和原生云端入口验证成功。
- 真实备份可恢复且最终全量/增量对账一致；期间只有一个主写。
- 真实核心业务闭环及 AWL 重复/超时/中断恢复通过。
- 回滚演练、观察窗口和旧资源关闭后复验有证据。
