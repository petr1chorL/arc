## 第一性原理核查

底层目标是让一个固定版本 Workflow 在短生命周期函数之间可靠推进，并能在同一条业务链上
完成审核、评分、整改和追踪。搬迁路由或使用 `step.run` 本身不等于完成这个目标。

必要对象是业务 Operation、Run、NodeAttempt、固定输入/版本、租约与领取代次、外部调用账本、
事件 Outbox、HumanTask/Decision/ResumeRequest、Evaluation、ArtifactVersion 和关联 Trace。
数据库事务决定业务状态；AWL 负责唤醒，不作为业务授权或外部动作只执行一次的证明。
04E 已提供固定版本入口，因此现在实施运行链比继续扩充资产 CRUD 更接近用户目标。

## 本轮新证据

- `scripts/inspect-runtime-delivery-baseline.py` 使用内存 SQLite 和计数发送器，无外部请求。
  首次发送确认后回滚数据库，随后重试：同一事件调用发送器 **2 次**，最终状态仍为 `sent`。
  这证明旧通知实现存在确认与提交之间的重复窗口；不是 Netlify 迁移测试通过。
- 当前 `@netlify/async-workloads@0.0.106` 在 callback 返回之后保存检查点，不能消除上述窗口。
  `client.send()` 部分失败返回 `sendStatus: failed` 而非抛异常；发送方必须检查结果。
- 现有创建运行默认同步；评分、回归批次、整改复测和人工恢复也包含同步长操作。
  不应假定它们一定在函数请求时限内完成。

## 需要确认的业务契约取舍

### 1. 长操作的响应

推荐原生运行模式采用 `202 Accepted` + 持久化 `operationId` 和查询入口；页面显示排队、
运行、等待审核、结果待核对和终态，完成后查询原有业务结果。短事务与只读接口保持原语义。
明确区分“请求已接收”“模型调用完成”“评估完成”“运行完成”，不把 202 显示为成功完成。

替代方案是内部仍持久化排队，HTTP 请求有限等待，快速完成返回旧 DTO、未完成返回 202。
它能保留部分旧调用体验，但形成双响应契约，调用方依然必须处理异步。
无限同步等待不能作为迁移方案。推荐统一异步，以便前端、重试和取消使用同一个契约。

### 2. 无法确认结果的外部调用

推荐：先持久化调用意图、固定请求摘要和稳定调用键，再外发。接收方有已验证的幂等或
结果查询协议时，按该协议恢复；没有这些能力时，发送后发生超时、断连或进程丢失，
进入 `needs_reconciliation`，**暂停自动重发，不自动判为成功或普通失败**。
人工核对入口应记录授权人、依据和决定；重新执行必须显式确认可能重复调用，并作为新尝试追踪。
租约过期只能证明原执行者失去写入资格，不能证明外部动作没有发生。

替代方案是直接自动重试：可用性较高，但可能重复模型计费、HTTP POST 或通知，
与当前“重复事件不产生重复业务副作用”的验收标准冲突。推荐保守核对策略。

上述两项会改变既有 API/恢复体验。用户在本提案提出后回复“同意”，确认统一异步与
结果不确定时暂停自动重放的规则。按此范围连续实施；生产发布与切流仍不包含在本轮内。

## 迁移行为与旧实现边界

以下路径均位于 `/api/workspaces/{workspace}`；表内“拟迁移”不是完成声明。

| 链路 | 当前实现 | 拟迁移行为 |
|---|---|---|
| `/workflows/{id}/runs`、运行重跑/失败节点恢复 | 创建默认同步，可显式入队 | 固定 WorkflowVersion 和输入，持久化 Operation 后返回 202；取消和重投可追踪 |
| `/execution-jobs` 与 heartbeat/requeue/cancel | 普通读取后领取，无领取代次防护 | 原子领取、租约、代次校验；旧执行者不得覆盖取消或新尝试；事件重复仅唤醒同一业务任务 |
| HumanTask claim/transfer/decisions/retry-resume | 认领、会签、决定、恢复；恢复包含同步执行 | 锁定参与者/任务状态，决定与恢复意图原子提交；重复决定校验完整请求；恢复持久化排队 |
| `/evaluations/rubrics/{id}/evaluate` | 同步调用 Judge | 异步 Operation，持久化实际模型返回后的逐维分数、理由、成本、模型/量规版本 |
| `/evaluations/regression-runs` | 同步逐样本执行后生成已完成记录 | 批次先落盘，逐样本记录进度和失败；不能把部分完成显示为整个批次成功 |
| Remediation activities/retest | open/in_progress/done；复测原 Artifact | 保留任务/活动与评分关联；复测异步化，仍是用当前有效量规重评原产出物，不冒称重新运行修复后的 Agent |
| `/artifacts`、运行详情和 Observability | 存在版本化产出物；部分 GET 回填 Trace 或 SLA | 同 Workspace 的版本化产出物和关联追踪；新记录在写入时关联，不靠读取时伪造完整链路 |
| 通知渠道、Outbox dispatch/requeue | 默认 in_app Noop；没有完整外部渠道发送适配器 | 区分站内持久化、真实发送确认、失败和待核对；渠道登记不等于真实发送能力 |
| Schedule CRUD/pause/resume/trigger/dispatches | 五段 cron、IANA 时区、固定版本；跳过漏掉的周期与重叠 | 保持这些调度语义；数据库唯一调度槽和事务 Outbox，定时函数只做有界派发，不执行整个工作流 |

现有节点引擎主要特别处理 Agent、Evaluation、Human，其余类型存在透传行为。
本次迁移不把透传包装成已实现的通用代码、条件或独立 Tool 节点引擎。
旧 `/reviews/{id}/decision` 可绕过 HumanTask 链；原生模式不得用该入口绕过会签。
关联 HumanTask 的写入必须进入统一决定链；仅有旧 Review 的历史记录保持可查询，
不能推断或伪造新参与者和审核决定。该约束需纳入最终路由契约测试。

## 推荐数据流与失败处理

1. 用户写入入口校验 Session、CSRF、角色、Workspace、幂等键与请求摘要。
   同一 PG 事务保存 Operation、业务状态及待发送事件，提交后才返回接收结果。
2. 有界派发读取 Outbox，以稳定业务 ID 唤醒 AWL；确认发送成功后更新派发状态。
   AWL 发送重试可以产生多个事件 ID，消费端仍只能领取同一个业务尝试。
3. 消费端回查任务，不信任事件中的业务权限或业务正文；使用原子领取和代次隔离。
   调用前固化版本、输入和工具结果，避免恢复时把新资产版本混入旧运行。
4. 单次节点执行有界，结果分步提交；外部结果不确定进入待核对。普通纯计算或
   已证实未发送的可恢复失败才进入有界重试、退避和死信策略。
5. HumanTask 暂停不占用执行函数；决定和恢复请求落盘后由同一消费机制继续。
   取消限制后续推进；不能承诺撤销接收方已经执行的动作。
6. 状态变更同时记录审计与 Trace 关联。页面刷新或重连从持久化状态恢复，不依赖
   一次请求的本地 Promise。错误输出应脱敏，不记录凭证或原始敏感异常。

默认仍休眠交付：业务函数进入 DB/AWL 前拒绝，业务事件订阅为空，不注册业务 schedule，
不在 import/build 时发事件；前端不把原生资产 ID 送给旧生产数据库。
后续启用与数据切换属于第 5 项，不能用本地验证代替。

## 实施与验收边界

设计确认后再形成准确文件级 TDD 实施计划，按端到端切片连续推进 05、06：
运行提交到可查询结果；恢复/取消/重试；通知与调度；人工审核继续运行；评估/整改/产出物/追踪。
这些是实施顺序，不是每完成一小片就要求用户再批准的停止点。

完成 05/06 本地工程至少需要新的以下证据：

- 共享 HTTP 契约与角色/Workspace/CSRF/重复请求边界，前端处理 202 与全部非终态。
- 实际 PG 竞争验证：同时领取、代次过期、取消对完成、重复调度、重复决定及恢复。
- 合成外部适配器故障注入：发送前、确认后提交前、检查点失败、重复事件与部署式进程中断。
  无幂等接收方不得自动重复外发；支持幂等的接收方恢复必须固定请求和调用键。
- 人审认领/转交、any_one/all/threshold 会签、驳回、修改产出物并批准、失败恢复和权限撤销。
- Judge 实际适配器的请求/解析与受控返回测试；批次部分失败、复测、逐维理由与成本持久化。
  Fake/受控响应只能证明工程链路，不是付费真实模型质量验收。
- Artifact 版本不覆盖，Run/Node/Decision/Evaluation/通知/审计可按同一业务 Trace 关联；查询分页有界。
- lint、build、相称的完整回归及浏览器端到端验证；休眠入口与构建产物检查。
- 第一性原理与对抗式审查记录、Issue AC 逐项回执、事实文档同步。

## 对抗式审查（设计阶段，未放行）

已识别：外部确认与 DB 提交不原子；AWL 不是 exactly-once；取消可能被旧执行者覆盖；
同步批量评分产生已调用但未记账窗口；Noop 冒称真实通知；旧 Review 入口绕过完整审核；
历史 trace 回填不等于真实因果追踪；休眠开关不能只依赖 SDK eventFilter。
以上均须在实现与测试中处理，当前不标记已修复。
